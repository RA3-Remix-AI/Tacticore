# 本机既有运行的独立控制通路 · 2026-10-29

连接保存中断可能留下“库已更新、注册仍旧”。普通准入必须继续拒绝这一状态，但已登记运行的观察、停止和诊断不应依赖连接库恢复成功。旧 Rust 路由先对所有请求核对库与注册，因而 Python 中已有的控制例外未真正可达；旧问题原件保留。

新通路只接收四个既有命名操作：`run.resume`、`run.status`、`run.stop`、`diagnostics.export`。Rust 从当前进程的原生 `LOCALAPPDATA/Tacticore/desktop-runtime` 选择状态来源；WebView 只能提交操作所需的运行/会话 UUID，不能提交路径、PID、命令或可执行文件。普通 `source_at` 的库/注册哈希核验保持严格；检查、启动、配置、风格和会话操作不会降级进入控制通路。

独立 Python 服务 `control_only_server_v1` 只有状态目录，没有连接库、档案或凭据接口。它复用真实 `DesktopBackend` 的 launch index、journal、会话绑定、停止意图持久化和诊断脱敏：停止仍核对已有运行、会话 UUID、游戏 PID 与创建时间；写停止请求不等于已停止或已独立归还。未知写入保留 uncertain，不自动重试。它只有原宿主身份查询能力，创建 Host 和新准入被硬拒绝。

没有既有账本时，恢复观察返回无运行且不创建数据库，避免破坏首次初始化。缺少一半账本时拒绝，不伪造空历史。诊断使用原运行保存的配置快照，缺失时如实标记，不读取当前连接库或密钥。

Rust 控制服务拥有独立 mutex 和子进程，不与普通/配置服务的交换共锁，因而不会被坏配置管道的 60 秒等待排队。四个控制操作在自己的管道内仍串行；这不承诺任意情况下立即停止。

离线验证包括真实隔离 Python pipe 上四个操作、错误会话与进程身份、unknown 不重发、拒绝全部其他命令和额外路径/PID、首次空状态无写入，以及 Rust 实际 dispatch 在坏注册和持有配置锁时的行为。所有样本均为 D 盘人工账本和假运行，无真实用户库、游戏或模型访问。新 EXE 的真实 WebView 控制通路仍待实测；完整 F05/F06 与正式三局未因此通过。

release companion 的源码收集会递归包含新非测试模块；本次没有建立大型发布包，发布包完整性与真实安装环境仍待验。旧实际 GUI 构建、隔离首用/重开/恢复、pending 状态按钮缺口及其新 UI 修复分别保留，不在旧记录补标通过。
